------------------------------------------------------------------------------
1) WHY VFIO EXISTS (THE CORE PROBLEM)
------------------------------------------------------------------------------

Classic Linux networking model:

    NIC
     |
     |  DMA
     v
 Kernel Driver
     |
     |  copy + syscalls
     v
 User Application

Problems:
- Kernel owns the device
- Kernel owns DMA buffers
- User space cannot:
    * program device registers
    * control DMA
    * do zero-copy RX/TX
- Performance limited by:
    * interrupts
    * skb allocation
    * memory copies
    * context switches

DPDK wants:

    NIC
     |
     | DMA
     v
 User Space (DPDK)

This is EXTREMELY dangerous unless hardware-enforced isolation exists.

That isolation mechanism = IOMMU
That userspace framework     = VFIO

------------------------------------------------------------------------------
2) WHAT VFIO IS (IN ONE SENTENCE)
------------------------------------------------------------------------------

VFIO (Virtual Function I/O) is a Linux kernel framework that allows a PCI
device to be SAFELY controlled from user space using IOMMU-based DMA isolation.

------------------------------------------------------------------------------
3) CORE COMPONENTS (LOCK THIS IN)
------------------------------------------------------------------------------

VFIO is NOT one thing. It is a stack:

    +--------------------------+
    |  User Space (DPDK)       |
    +--------------------------+
              |
              | ioctl(), mmap()
              v
    +--------------------------+
    |  vfio_pci (kernel drv)   |
    +--------------------------+
              |
              | IOMMU mappings
              v
    +--------------------------+
    |  IOMMU (hardware)        |
    +--------------------------+
              |
              | DMA translation
              v
    +--------------------------+
    |  PCI Device (NIC)        |
CPU MMU:
    VA (process) -> PA (RAM)

IOMMU:
    IO_VA (device) -> PA (RAM)

Without IOMMU:
    NIC can DMA to ANY physical address
    -> kernel memory corruption
    -> full system compromise

With IOMMU:
    NIC can DMA ONLY to whitelisted pages

------------------------------------------------------------------------------
5) WHAT IS A VFIO GROUP (VERY IMPORTANT)
------------------------------------------------------------------------------

A VFIO GROUP is the SMALLEST set of PCI devices that CANNOT be isolated
from each other by the IOMMU.

Rule:
    If device A can DMA to device B’s memory,
    they MUST be in the same IOMMU group.

Why?
    Because isolation is impossible between them.

Example:

    PCIe Root Port
        |
        +-- NIC 0000:01:00.0
        +-- NIC 0000:01:00.1   (same group)

Reason:
- Same PCIe switch
- No ACS (Access Control Services)
- DMA paths not distinguishable

Kernel rule:
    VFIO allows access ONLY at GROUP granularity.

You NEVER bind a single device.
You bind the ENTIRE group.

------------------------------------------------------------------------------
6) HOW DEVICES IN A GROUP CAN ACCESS EACH OTHER'S MEMORY
------------------------------------------------------------------------------

Without proper ACS:
- PCIe switch forwards DMA blindly
- IOMMU sees traffic as coming from the same requester
- Device A can DMA into memory assigned to Device B

Thus:
    Isolation boundary == VFIO group

------------------------------------------------------------------------------
7) VFIO DRIVERS (CLEAR THIS CONFUSION)
------------------------------------------------------------------------------

VFIO is a FRAMEWORK.
Drivers are PLUGINS.

Main VFIO drivers:

1) vfio_pci
   - For PCI devices (NICs, GPUs)
   - Used by DPDK
   - Handles BAR mmap, DMA mapping

2) vfio_platform
   - For non-PCI SoC devices (ARM)

3) vfio_ccw
   - For IBM mainframe devices

For DPDK:
    vfio_pci is EVERYTHING.

------------------------------------------------------------------------------
8) WHAT vfio_pci ACTUALLY DOES
------------------------------------------------------------------------------

When you bind a NIC to vfio_pci:

1) Kernel unbinds normal driver (ixgbe, i40e, etc)
2) vfio_pci claims the device
3) Device becomes invisible to kernel networking stack
4) vfio_pci exposes:
    - BARs via mmap()
    - DMA API via ioctl()

------------------------------------------------------------------------------
9) BAR MAPPING (REGISTER ACCESS)
------------------------------------------------------------------------------

NIC exposes BARs (Base Address Registers):

    BAR0 -> control registers
    BAR2 -> queue registers
    BAR4 -> stats, etc

vfio_pci:
    mmap(BARx) → user space

Result:

    User Space Virtual Address
           |
           v
    NIC MMIO Registers

DPDK now does:

    * queue setup
    * descriptor programming
    * interrupt masking
    * NIC configuration

DIRECTLY from user space.

------------------------------------------------------------------------------
10) DMA MEMORY PROBLEM (THE HARD PART)
------------------------------------------------------------------------------

NIC DMA requires PHYSICAL addresses.

But user space only knows VIRTUAL addresses.

Solution:
    VFIO + IOMMU

------------------------------------------------------------------------------
11) HOW DPDK REGISTERS HUGEPAGES WITH VFIO
------------------------------------------------------------------------------

Step-by-step RX/TX buffer setup:

1) DPDK allocates hugepages
   - 2MB or 1GB
   - pinned (non-swappable)

2) DPDK gets IOVA (IO virtual address)
   - via rte_mem_virt2iova()

3) DPDK calls VFIO ioctl:
   VFIO_IOMMU_MAP_DMA:
       {
         iova  -> device-visible address
         pa    -> physical address
         size
         perms
       }

4) IOMMU programs its page tables

Now:

    NIC DMA → IOVA → IOMMU → Physical RAM

Safe. Isolated. Zero-copy.

------------------------------------------------------------------------------
12) PACKET FLOW WITH VFIO (TRUE ZERO COPY)
------------------------------------------------------------------------------

RX path:

    NIC
     |
     | DMA
     v
 mbuf data buffer (hugepage)
     |
     v
 DPDK app reads packet

TX path:

    DPDK fills mbuf
     |
     v
 NIC DMA reads mbuf
     |
     v
 wire

NO kernel
NO copy
NO skb
NO syscalls

------------------------------------------------------------------------------
13) WHAT THE PMD DOES (IMPORTANT)
------------------------------------------------------------------------------

vfio_pci ONLY provides:
- register access
- DMA permission

PMD (Poll Mode Driver) provides:
- NIC-specific logic

PMD responsibilities:
- Initialize queues
- Program descriptors
- Poll RX rings
- Refill mbufs
- Handle TX completion
- Understand NIC quirks

Think:

vfio_pci = door + electricity
PMD      = driver brain

------------------------------------------------------------------------------
14) WHAT IF NO VFIO / NO IOMMU
------------------------------------------------------------------------------

Case: IOMMU disabled or unavailable

Result:
- DMA isolation impossible
- VFIO unsafe
- Kernel REFUSES vfio_pci

DPDK fallback:
    UIO (igb_uio / uio_pci_generic)

Problems with UIO:
- No DMA protection
- Device can corrupt kernel memory
- Unsafe for production
- Still zero-copy, but dangerous

------------------------------------------------------------------------------
15) IF NOT VFIO, HOW DOES DPDK GET PACKETS?
------------------------------------------------------------------------------

Option 1: UIO
    - Direct NIC access
    - Unsafe DMA

Option 2: AF_PACKET (vdev)
    - Kernel owns NIC
    - One copy per packet
    - Uses PACKET_MMAP (TPACKET)

Option 3: TAP / virtio-user
    - Software devices
    - More copies
    - Lower performance

------------------------------------------------------------------------------
16) AF_PACKET (TPACKET) PATH (FOR COMPARISON)
------------------------------------------------------------------------------

RX path:

    NIC DMA → kernel skb
               |
               | copy
               v
        PACKET_MMAP ring
               |
               | mmap (no copy)
               v
            DPDK app

Exactly ONE copy.
Kernel always involved.

Command:
    --vdev=net_af_packet0,iface=eth0

------------------------------------------------------------------------------
17) IS VFIO ONLY FOR VMs?
------------------------------------------------------------------------------

NO.

VFIO is for:
- VMs (QEMU passthrough)
- Containers
- Bare-metal DPDK
- GPU compute
- FPGA access
- High-speed I/O apps

VFIO = general-purpose safe userspace device access.

------------------------------------------------------------------------------
18) FINAL MENTAL MODEL (MEMORIZE THIS)
------------------------------------------------------------------------------

Without VFIO:
    Kernel owns device
    Kernel owns DMA
    Copies everywhere

With VFIO + IOMMU:
    User owns device
    Hardware enforces safety
    DMA is direct and isolated
    Performance is maximal
